-- Build configuration --
All benchmark numbers in results.md are from Release builds only (dotnet build src/Tckr.slnx -c Release).
Tckr.MockExchange.csproj sets ServerGarbageCollection=true, ConcurrentGarbageCollection=true
(see the csproj comment: this process is throughput-oriented and gets its own GC heap/thread
rather than contending with socket writes for one; background collection keeps a gen2 out of
the middle of a benchmark window).
TieredCompilation / TieredPGO: left at their .NET 10 defaults (both on) — not overridden by
the csproj or by any benchmark script env var.

-- Topology --
Tckr.MockExchange (the load source) and Tckr.FeedProbe (the measuring client) run on the
SAME host for every Phase 2 run — there is no second machine available. This means:
  * Delivery-latency figures in every scenario are same-host-clock figures, not network
    latency; they become unreliable the moment ingestion and exchange are on separate boxes.
  * Every CPU% figure reported is 'this host running both processes', not the exchange alone.
    Where it matters, results.md reports the exchange process and the probe process separately
    (via 'ps -o pcpu,rss -p <pid>' sampled every 5s) so the split is visible.
